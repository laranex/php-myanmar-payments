# Changelog

All notable changes to `php-myanmar-payments` will be documented in this file.

## v4.0.0 - Unreleased

Initial release. The version starts at v4.0.0 so that it lines up with the other Laranex Myanmar payments packages, which share the same gateway behavior and release cycle.

### Added

- Framework-agnostic SDK for KBZ Pay (PWA, QR, In-App), Wave Pay, AYA Payment Gateway, Yoma MMQR and CyberSource Secure Acceptance: `KbzPay`, `WavePay`, `AyaPay`, `YomaMmqr` and `CyberSource`, each implementing the `PaymentGateway` contract.
- `MyanmarPayments` builds every gateway from one configuration array, creating each gateway on first use.
- One typed configuration class per gateway (`KbzPayConfig`, `WavePayConfig`, `AyaPayConfig`, `YomaMmqrConfig`, `CyberSourceConfig`) and one typed request class per gateway (`KbzPayPaymentData`, `WavePayPaymentData` with `WavePayItem`, `AyaPayPaymentData` with `AyaPayMethod`, `YomaMmqrPaymentData`, `CyberSourcePaymentData` with `CyberSourceTransactionType`).
- One result class per flow: `RedirectPayment`, `FormPayment`, `QrPayment` and `AppPayment`, all implementing `PaymentResult` and tagged with a `PaymentFlow`.
- Verified callbacks: `handleCallback()` accepts a `CallbackRequest` (`CallbackRequest::fromGlobals()` or any PSR-7 server request) and returns a `PaymentCallback` with a gateway-independent `PaymentStatus` and the `Acknowledgement` each gateway expects. Query strings (`fromGlobals()` reads `QUERY_STRING`, `fromPsr7()` the request URI) and urlencoded bodies are decoded alike: names are kept exactly as sent and the first value of a repeated name wins.
- Status checks for KBZ Pay, AYA Payment Gateway and Yoma MMQR return `PaymentStatusResult`. Yoma MMQR treats an empty `errorCode` as no error and takes the error message from `errorDescription`, then `error_description`; KBZ Pay's `callbackInfo` is sent URL-encoded with `~` kept as is.
- Callback, return and cancel URLs only need to be valid absolute http or https URLs (PHP's `FILTER_VALIDATE_URL` rules: printable ASCII, an ASCII host name or bracketed IP, a port up to 65535); there is no HTTPS-only or port-443 rule (gateways may still require HTTPS in production).
- Wave Pay follows the Pay with Wave API spec v1.3: payments are a JSON post to `base_url`'s `/payment` (Content-Type and Accept `application/json`) with `amount` and `time_to_live_in_seconds` as JSON integers (amounts with every digit, no integer limit; without `amount` the total is the exact sum of the items), `currency` `MMK` and `items` as a JSON string array, and the customer is sent to `base_redirect_url`'s `/authenticate` (`transaction_id` URL-encoded with `~` kept as is; UAT: `https://preprodpayments.wavemoney.io:8107` for both; production: `https://payments.wavemoney.io`). `WavePayPaymentData` takes optional `additionalField3`, `additionalField4` and `additionalField5` (at most 50 characters each, sent as `additional_field_3` to `additional_field_5` only when set) and enforces the spec's limits: `orderId` and `merchantReferenceId` at most 100 characters, `callbackUrl`, `returnUrl` and `description` at most 255. Item names and amounts and the total are checked after the other fields; no items and no `amount` reports `The amount field is required.`, and an item amount that is invalid or has decimals skips the total check. A failed request's message lists `errors` only when it is a JSON object (each entry a message or a list of them), and `gatewayCode` is `VALIDATION_ERROR` whenever `errors` is present, even null.
- Wave Pay callback statuses per the spec: `PAYMENT_CONFIRMED` is successful; `BILL_COLLECTION_FAILED`, `INSUFFICIENT_BALANCE` and `ACCOUNT_LOCKED` are failed; `SCHEDULER_TRANSACTION_TIMED_OUT` (and `TRANSACTION_TIMED_OUT`) is expired; `PAYMENT_REQUEST_CANCELLED` is canceled.
- Wave Pay callbacks fall back to `merchantReferenceId` for the order id when `orderId` is missing, null or empty (same rule as `go-myanmar-payments`).
- Callback and response JSON is decoded with numbers kept as their exact text (strings), so a gateway sending `1000.50` or `1000.0` as a JSON number still verifies; booleans sign as `true` / `false`. Response and callback fields are read as text the same way (a boolean is `true` / `false`, an object or list is no value), and only ASCII whitespace and NUL are trimmed (a no-break space or byte order mark is kept).
- Callback verification rejects nested (non-scalar) values in signed fields instead of casting them, and CyberSource rejects a post whose `decision` or `req_reference_number` is not listed in `signed_field_names`, reads `transaction_id` and the amount only when signed, and keeps only the signed fields plus `signature` in `raw`.
- Signed callbacks can't be re-split: AYA Pay requires `merchOrderId`, `tranId`, a decimal `amount`, currency `104` and a two-digit `statusCode`, and allows ":" only in `dateTime` (payments reject ":" in `orderId`, `description` and `userRefs`); CyberSource requires `signed_field_names` to list itself with unique names free of "=" and a documented `decision`; Wave Pay requires a decimal `amount` and `orderId` / `merchantReferenceId` of letters, digits, `_` and `-`, in callbacks and in new payments. A bad signature, hash or checksum throws `... verification failed.`; a check that fails after it matched throws `Wave Pay callback is malformed.`, `AYA Pay {callback|redirect|enquiry response} payload is malformed.` or `CyberSource callback is malformed.` (CyberSource's missing signed `decision` / `req_reference_number` and unknown decision included). `FormPayment::toHtml($nonce)` takes a CSP nonce.
- AYA Pay reads a base64 `payload` whose `+` arrived as a space as `+` (the checksum is still verified). `services()` reads `data` and each service's `methods` only as JSON lists and skips method entries that are not scalars.
- `Amount::parse()` drops leading zeros of the whole part (`007.50` becomes `7.50`).
- Exact `Amount` values (`Amount::kyat(1000)`, `Amount::parse('1000.50')`) instead of floats; decimals are allowed only where the gateway's official documentation allows them. A negative whole number given to a payment data class or `WavePayItem` is reported with the other invalid fields (`The amount field must not be negative.`, `items.<i>.amount` for an item).
- HTTP through any PSR-18 client (auto-discovered via `php-http/discovery`) and Yoma MMQR tokens cached through any PSR-16 cache, with an in-memory `ArrayCache` as the default.
- Exceptions: `PaymentException` as the base, with `ApiException`, `ConfigurationException`, `InvalidPaymentDataException` and `SignatureVerificationException`.
- Configuration: every setting of a gateway you use is required and has no default, except the HTTP timeout (`timeout_in_seconds`, `MYANMAR_PAYMENTS_HTTP_TIMEOUT`), which defaults to 30 seconds (`MyanmarPayments::DEFAULT_TIMEOUT_SECONDS`). That includes the URLs, the time to live (KBZ Pay's `time_to_live_in_minutes`, 1 to 120; Wave Pay's `time_to_live_in_seconds`, greater than 0) and Yoma MMQR's `webhook_secret` (checked on every callback's `X-Webhook-Secret`). A missing or blank setting throws the `ConfigurationException` naming it (public `gateway` and `key`); a value out of range throws `ConfigurationException::invalid()`, e.g. `The kbz_pay configuration [time_to_live_in_minutes] must be a whole number from 1 to 120.` Whole-number settings hold at most 2147483647. Settings given in an array may be text or integers (`'merchant_code' => 200123`); floats and booleans count as missing. Settings are checked in a fixed order: the required strings, then the time to live, then the timeout.
- Time to live per payment: `KbzPayPaymentData`'s `timeToLiveMinutes` (1 to 120) and `WavePayPaymentData`'s `timeToLiveSeconds` override the configured value. `WavePayPaymentData` also takes an optional `merchantName` that overrides the configured one. CyberSource payments take `currency`, `locale` and `transactionType`.
- `fromEnv()` on every config class, every gateway and `MyanmarPayments`, reading the same variables as the other SDKs (`KBZ_PAY_*`, `WAVE_PAY_*`, `AYA_PAY_*`, `YOMA_MMQR_*`, `CYBER_SOURCE_*`). Gateways and `MyanmarPayments` entries accept a config object or its `fromArray()` array.
- `Amount::equals()` (by value, ignoring leading and trailing zeros) and JSON serialization of `Amount` as a string; `PaymentStatus::resolve()`; `Acknowledgement::default()`; `CallbackRequest::queryInput()`; `FormPayment::field()` and `values()`; a public `validate()` on every payment data class; a public `KbzPay::$signer` and `KbzPaySigner`.
- Behavior is identical to `go-myanmar-payments`, `node-myanmar-payments` and `python-myanmar-payments`, checked by the shared vectors in `tests/Fixtures/parity/vectors.json`: signing, callback decoding, AYA's base64 rules, the Yoma MMQR token cache key (`myanmar-payments.yoma-mmqr.token.<sha256 of base URL|client id>`), `FormPayment::toHtml()`, URL validation, query escaping, whitespace trimming, configuration and validation order, and every error message.
- Requires PHP 8.1 or higher; tested on PHP 8.1 through 8.5 with Pest, PHPStan (level 7) and Pint.
- Agent skill in `skills/php-myanmar-payments` so coding agents (Claude Code, Codex, Cursor and others) integrate the SDK correctly; install it with `npx skills add laranex/php-myanmar-payments`.
